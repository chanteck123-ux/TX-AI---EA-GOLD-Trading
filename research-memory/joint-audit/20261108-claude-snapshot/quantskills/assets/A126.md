## P0129 部分（FILE 1323 conversion_report、1324 etf_timing_conversion_report、1325 README.en、1326 README 全文）

要点：
- 把聚宽（JoinQuant）策略按"理解意图，而非逐行翻译"的原则迁移为 PandaAI 的 JSON 或 code_blocks 格式，并输出转换报告与核对清单。

独立发现（对示例代码做文本推导，**未运行**）：
1. **转换后的 ETF 择时策略引入了前视**：
   - 映射表写 `run_daily(func,'open')` → "handle_data runs before open"；
   - 但 handle_data 中：
     - 择时用 `get_market_data(start=today, end=today, fields=['high','low'])`，取的是**当日**最高价与最低价；
     - 止损用 `end_date=today, count=10` 的收盘序列，最后一个就是**当日**收盘价；
     - 买入价用 `data[...].close` 或当日收盘价；
   - 原策略的止损在开盘时运行，择时在 9:40 运行（报告自述），不可能看到当日完整的 K 线。
   
   转换在开盘前使用了当日的高、低、收数据，会显著美化回测。
2. **月度轮动实际上失效**：
   - `is_monthly = (run_day == 1) or (to_hold == '')`；
   - run_day 每根 K 线加 1，从不重置；run_day == 1 只出现在第一天，而第一天被 `context.first` 直接 return；
   - 因此"月度轮动"只会在 to_hold 为空时触发（初始化或止损之后），首次选中的 ETF 会一直持有到止损；
   - 报告 Caveat 3 称"当前版本在 signal = 1 时每天检查"，与代码不符；核对清单却勾选了 "[x] Monthly ETF rotation"。
3. **状态语义被改变**：
   - handle_data 每天先把 `signal = -1`（看空）作为默认值，|z| ≤ 0.7 的中性区因此一律视为看空，转入债券；
   - 原策略在中性区是否维持上一次信号（迟滞），需要对照原代码。转换报告没有讨论这一点。（需核对原始源码，**未核实**。）
4. 止损后 to_hold 被清空，若次日 signal 仍为 1，会立即重新选择——可能买回刚刚止损的同一只 ETF。
5. "260 根日线首末收盘价比"被称为"比月线收益更精确"，实际是另一个指标（窗口与端点都不同），并非等价转换。
6. ETF 与债券基金使用 `type='stock'` 取数；JSON 输出中的 code 字段是 "[SEE ABOVE…]" 占位符，**不能直接导入运行**，与"可直接运行回测"的说法不符。
7. MA 交叉示例中，"持仓检查：隐式？需要验证"仍是未解决的疑问，核对清单却全部勾选。**核对清单都是自评勾选，没有一项与原平台的回测结果比对。**

与黄金 EA 的关系：**相关（跨引擎迁移的反面教材）**。本项目的 LEAN（C#）研究端与 MT5/MQL5 执行端之间的移植核对可以借鉴：
- 逐个事件的时点对照（何时触发、能看到哪些数据：当根 K 线还是上一根已收盘的 K 线）；
- 状态变量的初始化与重置语义（计数器、中性区迟滞）；
- 调度语义（月初、每日固定时间）要有单元测试；
- 等价性必须通过同数据、同参数下的信号与成交逐条比对来确认，不能靠勾选清单。

以上对应 PLAN 中跨引擎核对的要求，只作为检查设计参考。

## P0130 补读（FILE 1327 batch_conversion、1328 jq_patterns、1329 panda_format、1330 panda_framework、1331 source_boundary 全文）

独立发现（文本推导，**未运行**）：
1. **资产自身的框架文档否定了 ETF 示例**：
   - panda_framework 写明：handle_data 中**禁止**调用 `panda_data` 网络请求，数据 API "只能在 initialize 和 before_trading 中调用"；
   - handle_data 的运行时间是"股票 9:30~15:00"，before_trading 是 8:30；
   - ETF 转换示例在 handle_data 中多次调用 `panda_data.get_market_data`，并声称"handle_data runs before open"。
   
   示例同时违反了框架约束，而且时点描述与框架文档矛盾。这进一步证实了 P0129 发现 1（前视）的成因：在日线 bar 内查询当日数据。
2. **"语义相同"的映射未经证实**：
   - jq_patterns 把 `attribute_history(s, c, '1d')` 映射为 `get_price(pro_code,'1d',count=c)`，称"Same semantics"；
   - 聚宽默认 `fq='pre'`（前复权），且在盘中调用时是否包含当日 bar 由平台规则决定；
   - PandaAI 一侧的复权口径和是否包含当日 bar 都没有说明；
   - `set_option('use_real_price')` 映射为"不需要"，但它影响的是下单价格与复权口径的关系，并非可以省略的设置。
   
   这类"同语义"判断都需要逐条用数据验证。
3. 错误映射：`is_st_stock(s)` → "检查代码后缀 .XSHG/.XSHE"。后缀只表示交易所，不能判断是否为 ST，属于事实性错误。
4. panda_format 中的时间表格自相矛盾：`month_day` + `freq_value=5` 被描述为"Every 5th trading day"，而注释又写"Trading day of month"，并允许 1–31（自然日范围）。
5. `amount` 的语义存在歧义：整数表示股数，小数表示比例。那么 amount = 1 是 1 股还是 100%？没有说明。
6. batch_conversion 文中写"递归扫描"，示例代码却用 `os.listdir`（不递归）；分类依靠代码子串匹配（如 `len(source_code) > 5000` 判为 custom_pool），只是启发式，不能决定转换格式。
7. 汇总模板中"API 使用热度表"标注 `get_fundamentals → get_factor() ✅ Full`，而 jq_patterns 自己又承认"复杂查询需拆分、指标可能不同"，两处不一致。

结论：A126 在本 manifest 中的文本已全文读完（FILE 1323–1331），SKILL.md 若在后续 pack 中则再补读；示例 .py/.json **未核查、未运行**。与黄金 EA 的关系维持 P0129 的结论：跨引擎迁移必须以数据逐条对照验证"同语义"，不能依赖映射表。

# A032 skill-b11-auto-stop-loss-take-profit（全文审核笔记）——与 RiskExecution 高度相关
- 读取（P0034）：INSTALL.md、README(.en.md, .md)、references/api_guide.md（SKILL.md 和脚本见后续包或不在清单内）。
- 内容：A 股和期货多头持仓的五级决策：
  - 守卫（输入异常 → hold）→ 次日高开止盈（+5%）→ 次日低开止损（−3%）→ 持仓 ≥2 个交易日强平 → 单票名义价值 > 总权益 10% 时减仓 → hold。
  - 输出 8 字段调仓指令，只会 sell/hold，不产生 buy。
  - 交易日历硬依赖 panda_data，本地 parquet 缓存。
  - 自述是对一个"52/100 验收版"的增强修复（E1–E6）。
- **值得借鉴（与项目规则一致或可作为候选）**：
  - ①**仓位分母用总权益（total_equity），不用可用资金**，且分子分母同口径（名义价值 = 数量 × 价格 × 合约乘数）。
  - ②**未知期货品种缺少合约乘数时直接报错，不静默按 1 计算**——作者原文："避免仓位上限失效"。对应我们的原则：GOLD 合约规格读取失败就拒绝新单，绝不默认取值。
  - ③持仓天数按交易日历计算（周五入场的"次日"是周一）；入场当天为第 0 天。
  - ④reason 字段带规则前缀，指令可追溯。
  - ⑤减仓目标按最小交易单位向下取整。
- **独立发现（风控设计缺陷，静态推理，未运行）**：
  - ①**输入异常时返回 hold = 退出路径 fail-open**：价格 NaN/inf、总权益 ≤0、today < entry_date，全部"静默 hold"。对一个止损模块来说，数据坏了却"什么也不做"，意味着保护失效且没有告警。正确做法是**升级处理**（告警、冻结新增风险、保留或采用保守保护），而不是安静地 hold——这与项目规则"已有仓位保护先于新增风险门控，不能被阻断"直接相关。
  - ②**保护依赖外部数据登录**：交易日历硬依赖 panda_data，没有回退方案；缓存不覆盖当天且凭证或网络失败时抛 RuntimeError——**止损引擎因为一个日历服务不可用而整体停摆**。批量 run 是否会因为一条记录报错而整批中止，文档没有说明。对应我们的设计：退出和保护路径不能依赖非必要的外部服务，失败时要降级为保守动作。
  - ③**只在开盘价上判断**：止盈止损只用 open_price，盘中跌破 −3% 不会触发，"次日"之后（第 2 天起）只有强平规则，没有价格止损。这是"按日开盘检查一次"的设计，不是真正的止损。
  - ④**上限无法执行时静默保留**：减仓目标取整后 <1 个单位就 hold，例如单手期货名义价值本身就超过权益的 10%，超限状态会无限期持续，只在 reason 中提示。应升级为告警或拒绝建仓，而不是长期容忍。
  - ⑤**期货用 A 股（SH）日历**：中国期货夜盘归属下一交易日，持仓交易日数对夜盘入场的仓位会算错；不区分涨跌停和停牌（作者已承认），触发日可能无法成交。
  - ⑥**文档残留**：INSTALL 中 Codex 工具的描述仍写"via injected holding_trading_days/trade_days"，而 v2 已删除这些入口。
  - ⑦api_guide 的示例用 `os.environ.setdefault("PANDA_PASSWORD", "...")` 在代码里写凭证，与"写入 shell 配置"的建议相矛盾。
- 测试：自述 68/68 通过、_verify_prod 实测通过——**未运行，只是资料陈述**。
- **对 RiskExecution（方案 B，Claude 负责）的意义——只记录候选，不改冻结 v1.0 接口**：
  - ①保护和退出路径遇到坏数据时：告警 + 冻结新增风险 + 维持或收紧现有保护，**禁止 fail-open 式 hold**；
  - ②合约规格或乘数缺失时：拒绝新单（fail closed）；
  - ③风险上限无法通过减仓满足时：升级处理并阻止同类新单，不长期容忍；
  - ④退出路径不依赖非必要的外部服务；
  - ⑤止损必须是持续生效的（服务器端 SL 加 EA 对账），不能只在某个时点检查。
  - 以上可作为故障注入测试的用例来源。
- 续读（P0035）：requirements.txt、SKILL.md（17 KB，全文）。补充核实：
  - 决策表确认：优先级 0 的守卫（today < entry、价格 NaN/inf、权益 ≤0）→ hold；止盈止损只在 holding_trading_days == 1 那天有效；≥2 天强平"target=0，不做手数取整"。**独立发现①③④得到原文确认**。
  - 失败降级写得清楚：refresh 失败**不删除**已有 parquet；过期 parquet → 实时拉取 → 再失败抛 RuntimeError（**独立发现②确认**：最终依赖外部服务）。
  - 写盘为原子替换，没有中间状态（好的做法，对应我们的状态持久化）。
  - Windows 用 `setx` 把密码写入用户环境变量，属于**明文持久化凭证**；本项目不能借鉴这种做法。
  - "其他交易所日历相同"的说法对期货夜盘不成立（**发现⑤确认**）。
- **A32 逐资产结论**：结构清楚、契约完整，但作为"风控"模块，存在 fail-open 守卫、依赖外部服务、只在开盘检查、上限静默容忍四个设计问题。**这是 RiskExecution 故障注入用例的好素材**。未运行，只阅读了文档，没有做静态实现核查（build.py 不在清单内）。

- **新发现**
  1. **CONFIRMED：批量运行时，一条坏记录会让整批停下。**
     - `run(list)` 先逐条执行 `validate_input`，任何一条不合法就抛出 ValueError，**整批不出任何指令**。这回答了文档层留下的问题。
     - 另外，未知期货前缀会在 `_resolve_multiplier` 里抛错。这一步在止盈、止损、强平判断**之后**执行，所以单条调用时退出规则仍然有效；但批量调用时，这个异常会中断 `batch_manage`，后面其他持仓的止损指令也一起丢失。
  2. **CONFIRMED：交易日历缓存只取第一次的结果，可能算错持仓天数。**
     - `_CALENDAR_CACHE` 是进程内的单例，第一次成功构造后，不管之后查询的日期范围是什么，都直接复用。
     - 如果第一次是用"第一条持仓的 entry 到 today"实时拉取的，后面 entry 更早的持仓用的就是一个不完整的日历。`trading_days_between` 会退回到 bisect 计数，从日历起点开始算，导致持仓天数**偏少**，强平被推迟，"次日"也可能判断错。
     - parquet 路径只检查 `max_date >= today`，不检查 `min_date ≤ entry_date`。
  3. 只支持多头：`current_qty` 必须 ≥ 0，盈亏按 (open − entry) / entry 计算。期货空单不能输入。
  4. 期货乘数写死在代码里，如 AU 为 1000、AG 为 15、SC 为 1000；查不到时报错，不会默认取 1。这一点与文档层的结论一致，做法正确。
  5. `build_calendar.py` 用 `.tmp` 临时文件加 `os.replace` 原子替换，失败时删除临时文件。原子写入得到 CONFIRMED。
  6. `_verify_prod.py` 的注释里有开发者本机的家目录路径，属于个人信息，本笔记不转录。它在运行时需要外部登录，本审核没有运行。

- 定位：把自然语言交易想法转成 SSQuant 策略代码，部署到 SIMNOW 模拟盘，再用 cron 每 5 分钟监控、推送和"自愈重启"，最后把这个交易员固化成新的 Skill 文件。中英文 README 一致。
- **对 V1.2 RiskExecution 有直接价值的反例（已核实原文）**：
  1. **仓位公式突破风险预算**：`volume = max(1, min(int(max_loss/(stop×mult)), max_allowed))`。止损距离较大时，int 向下取整为 0，再被 max(1, …) 强制成 1 手，实际风险超过 2% 预算且不留任何记录。这与 V1.2 §6.1–6.2"不自动扩大已授权风险"的原则正好相反。正确做法是返回 0 并标记 REJECT。
  2. **风控模板静默回退**：`equity = account.get('equity', 500000)`，取不到账户数据时假设 50 万；日亏损熔断按 initial_capital 计算，而不是按当日初始权益；如果 `get_account_info()` 返回空，整个风控层会被跳过（`if account:`），这是**失败放行（fail-open）**。
  3. **保证金 >70% 的分支并不阻止开新仓**：代码在 `pos != 0` 时直接继续进入策略层，注释"以下仅允许平仓逻辑"没有任何强制机制。
  4. **入场价记录错误**：模板 6 在下单后看到 `pos>0` 的第一根 bar 时，用 close[-1] 作为入场价；但下单类型是 `next_bar_open`，止损和跟踪基准都偏了。止损触发后会先清空 entry；如果平仓单还没成交、下一根 bar 仍有持仓，就会重新记录入场价，可能重复发出平仓单。
  5. **自愈重启时没有对账**：进程崩溃或"日志长时间不更新"时自动重启，但重启前没有对持仓、挂单和状态做任何对账，可能导致重复开仓或孤儿订单。V1.2 规定"对账先于新增风险"，此处正是反例。
  6. 混合模式中的 `ai_confirms_volume()` 读取 cron 每 5 分钟更新一次的状态，信号与确认之间存在时差，状态可能过期，文档没有说明 TTL。
  7. 涨跌停检测用"成交量为 0 且价格不变"来判断，流动性检测只看单根 K 线的量，都是粗略启发式。`rb888` 是连续合约代码，文档却建议直接用它报单，这属 PLAUSIBLE 待核实（通常需要映射到真实月份合约）。

## A196 结论
- 可借鉴：分级风控阈值表（警告、熔断、强平；按连亏笔数分级；保证金占用分级）、通知模板，以及"拿不准时宁可半自动"的思路。

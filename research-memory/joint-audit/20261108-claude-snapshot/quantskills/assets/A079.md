# A079 skill-factor-grouped-wrapper — 全文审核

## P0090 部分（FILE 876–878 全文：agents/portable-loader.md、README.en.md、README.md）

要点：
- 用于大规模因子库的分组贪心 Wrapper，模型为 CPU LightGBM，参数固定。
- 两种模式：Backward 从池 A 分组剔除；Forward 从池 B 分组加入。
- 主指标为验证期逐日截面 Pearson IC，或扣费对冲 Sharpe；每次接受须超过 `min_delta`。
- 多 seed 路径之后选唯一最佳；冻结后对原始 A、A* 与 final 做 OOS 回测，OOS 默认防覆盖。
- 标签：`trade_price` 次日执行的 1 日远期收益（execution_lag=1，horizon=1）。

独立发现（文档静态阅读，未运行）：
1. **单一验证年的多重比较**：模板为 2010–2021 训练、2022 单年验证。每轮评估全部 `current±group`，多 stage、多 seed 之后再按同一验证指标挑最佳路径。候选比较次数很大，`min_delta` 不足以控制选择偏差。文档已承认"可能过拟合验证期"，但未要求报告试验次数或做多重检验校正（同 A62 类）。
2. **seed 间二次选择**：多 seed 路径完成后，仍按同一验证期主指标选唯一最佳路径。"存活频率只作诊断"意味着没有使用比较稳健的共识集合。
3. **Sharpe 模式继承 A073 的问题**：每个验证候选都调用 skill-factor-backtest，因此继承其成本单位不一致（文档 ‱、代码 ‰）以及固定 9.5% 涨跌停判定（见 A073）。对冲 Sharpe 的基准和对冲方式需看 factor-backtest-integration.md。
4. **OOS 的三快照比较**：OOS 同时给出 A、A*、final 及相邻差值；若使用者据此挑选最好的快照，OOS 就变成了选择期。README 只说"OOS 不反馈到选择过程"，没有在报告层面规定只能有一个预先登记的晋级快照。
5. 训练期到验证期的边界 purge 或 embargo 未在 README 说明。horizon=1、lag=1 时影响小，留待读 algorithm.md 或 input_schema 时核对。
6. 说明较诚实："validation: runnable"只表示测试与合成 smoke 通过；平台入口不代表端到端认证；smoke 不调用 OOS。

与黄金 EA 的关系：
- 可借鉴：分组贪心搜索的可恢复 fingerprint 与冻结快照思想，对应我们的 candidate_id/run_id、冻结后验证、防覆盖。
- 必须同时登记试验次数并做独立样本验证。
- 不引入 LightGBM 或代码。

## P0091 补读（FILE 879–886 全文：references/algorithm、factor-backtest-integration、input_schema、output_contract、source_boundary、validation_notes、requirements、SKILL.md）

另做**选择性静态核查**（grep 定点读取，未运行）：
- `scripts/factor_grouped_wrapper/metrics.py` 112–131 行；
- A073 `BackTest.py` 303–359 行。

独立发现：
1. **切分边界的标签重叠（确定行为，按文档公式）**：`target[t] = trade_price[t+2]/trade_price[t+1] − 1`，而切分约束只要求 `train_end < valid_start`，没有 purge 或 embargo。训练期最后约 2 个交易日的标签使用验证期价格，验证期末同样跨入 OOS。OOS 阶段在 train+validation 上重拟合时，验证期末标签也用到 OOS 前 1–2 日价格。量级很小（horizon=1），但与"OOS 封存"的严格表述不符。
2. **成本参数继承单位歧义**：OOS 默认 `transaction=1.4`。若按 A073 代码 `/2/1000` 解释，等于往返 14 bp；若按其文档的"‱"理解，只有 1.4 bp。wrapper 文档未写单位。
3. **hedged NAV 列名核对**：`hedged_unrealized_pnl` 在 BackTest.py 354 行是 `cumprod × init_cash` 的净值，不是盈亏额，所以 wrapper 用 `pct_change()` 计算 Sharpe 是正确的，不存在我曾担心的 PnL 跨零问题。但对冲曲线（350–352 行）是"策略日收益×hratio − 基准日收益×hratio×hbili"按日复利，相当于每日再平衡、无基差、无对冲成本的理想对冲，对冲 Sharpe 会偏乐观（方向未量化）。
4. **wrapper 已避开 A073 的 DailyPCT 公式问题**：BackTest.py 319 行 `DailyPCT = diff(1)/当期值`，分母应为前一期，是 A073 自身的公式错误；wrapper 文档明确"Ignore DailyPCT"。
5. **缺失值填零**：按日变换后缺失值填 `fill_value`（默认 0，经 z-score 后相当于截面均值）。LightGBM 原生支持缺失，填零会抹掉"缺失本身"的信息；文档已披露，但未讨论影响。
6. **外部入口按路径搜索执行**：搜索顺序为 `backtest.skill_root` → 环境变量 → 同级目录 → `~/.codex/skills/...`，找到后以子进程执行。存在执行到非预期版本的供应链风险；建议锁定路径并核对版本或 hash。（仅文档描述；我们不安装、不运行）
7. 诚实度较好的地方：
   - 明确承认单一验证期重复比较会过拟合；
   - IC 与 Sharpe 目标可能分歧；
   - smoke 只验证机制；
   - OOS 有访问日志、防覆盖和 fingerprint；
   - `longx=50` 敏感性分析不得影响选择。
   
   第 4 点"三快照报告层选择"的风险仍未由文档约束。
8. `keep=0.8` 与 A073 文档的 0.7 不同，同一套件默认值不一致，只影响可比性。

与黄金 EA 的关系：可借鉴的工程化做法有：

这些与我们 run_id、证据留存、冻结后验证的要求一致。切分边界须按标签期限加 embargo（对应我们开发区间与独立样本之间的隔离）。不引入代码。

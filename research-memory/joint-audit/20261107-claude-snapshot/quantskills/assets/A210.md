- 定位：交易复盘。把已归并的平仓和未平仓记录转成汇总、归因、市场环境、逐笔点评、错误模式、建议和五档评级；数值由确定性代码计算，文字部分由宿主模型按原有插槽回填。中英文 README 一致。
- **优点（对 V1.2 有直接参考价值）**：
  - 硬性规定"LLM 不得改写任何数值字段"；
  - LLM 只能读取脱敏后的汇总数据，必须通过 tool use 输出 JSON 并做 schema 校验；
  - **每条 insight 的 evidence_keys 必须能在 attribution 或 context 中定位，否则丢弃**；
  - 失败时立即降级，不重试；
  - 归因满足会计恒等式（各 by_status 之和等于 total_pnl）；
  - 平仓样本少于 5 笔时评级强制降为 neutral；
  - 区分持仓方向与下单方向。
  "证据键必须可定位"这一做法可直接用于 V1.2 Critic 和监控类输出的校验。
- **问题**：
  1. **默认是否调用外部 LLM，文档互相矛盾**：README 和 SKILL 都说"默认不调用外部 LLM，可选、需显式启用"；llm_policy 却写"**默认开启（opus-4-7）**，走当前会话的 `ANTHROPIC_BASE_URL/API_KEY`"，示例 config 也写着 `enabled: True`。其中的模型名（opus-4-7、sonnet-4-6、haiku-4-6）只是"网关别名"，不是可核实的正式模型 ID；base_url 留空。如果按 llm_policy 执行，会在用户不知情的情况下把汇总数据发往第三方网关。
  2. **写入 Claude 配置目录**：缓存和审计日志写到 `~/.claude/skills/build-r00-trade-review/`，等于在用户的 Claude 配置目录下产生文件。Claude 不执行。
  3. **未平仓补价可能用错合约**：具体合约取价失败时，"用品种主力 `get_future_dominant` 兜底"。主力合约和持仓合约可能不是同一个月份，补出来的价格是错的，浮盈亏也就跟着错。再取不到价时浮盈亏直接记 0（有 warning），浮亏会被低估。这是 RiskExecution 对账中要避免的反例：**标记价格必须来自同一合约，取不到时应标为 UNKNOWN，而不是记 0**。
  4. **评分公式量纲混杂**：`alpha = total_pnl/(open_exposure + |realized_pnl|)`；胜率基线期货 40%、股票 50% 是拍定的；没有亏损时 profit_factor 为无穷大，输出 null，代入 tanh(null) 如何处理没有说明。`fee_drag` 用绝对金额 |PnL| < 50 作阈值，与账户规模无关。市场状态用 5 日年化波动判断，噪声很大。
  5. requirements 完全没有钉版本（pandas、numpy、requests、pyarrow 无版本号；anthropic>=0.40.0 只有下限）。27 个期货品种的合约乘数写在内置静态字典里，合约规格变更时不会更新。

- **主力合约兜底（PLAUSIBLE → CONFIRMED，且比文档层更严重）**：
  - `fetch_future_mark_price` 先取持仓合约的日线收盘；失败时改用 `get_future_dominant(...)["close"]`，即主力合约价格，用在另一个合约上，而且**不写任何 warning**。
  - 同一文件的 `load_future_context` 里，主力表需要与 `get_future_daily` 合并才能拿到 close，说明主力表本身多半没有 close 列。若如此，兜底分支实际返回 None，浮盈亏记 0 并写 warning（PLAUSIBLE，未连 SDK 验证）。
  - 无论哪一种情况，都**不会把结果标成 UNKNOWN**。
  - 期货技术指标用不同月份主力合约拼接的价格序列计算，换月处没有复权，MA、ATR 和前高前低都会在换月时出现跳变。
- **新发现（CONFIRMED，代码推演）**：
  1. **regime 波动阈值的单位错误**：`index_volatility_5d` 以百分数表示（`std×√252×100`，例如 20 表示 20%），`_infer_regime` 却用 `vol > 0.30` 判断高波动，于是只要年化波动超过 0.3% 就会被判为 `high_vol`，实际上几乎永远命中。结果是 `range_bound` 基本不会出现，"震荡市追突破"规则形同失效。同一套代码的其他地方都按百分数处理（`_bucket_vol ≥30`、`patterns <25`、`DEFAULT_VOL 20/25`），只有这一处单位不同。测试直接传入 `regime_label="high_vol"`，没有覆盖这条路径。
  2. **期货顺逆势拿股票大盘判断**：`_check_against_trend` 对非股票品种使用 `overall_regime`，而这个值优先取沪深 300 的趋势和波动（如 `stock_up_trend`）。只要账户里也有股票，做空螺纹就会因为大盘上涨被判为"逆势"，品种自身的 `futures[v].trend` 没有被使用。
  3. **"趋势"其实是单日涨跌**：`index_pct_pct` 和 `dominant_pct_pct` 都是最后一根与前一根收盘之比，`_bucket_pct` 据此划分 strong_up 到 strong_down。"5 日波动"是用 6 个收盘价、5 个收益年化得到的，噪声很大。
  4. **基差单位混用**：`future_context` 用 `basis or basis_rate`（优先取绝对价差，单位为元），配 `±0.005` 的阈值；`market_review` 展示时却优先取 basis_rate。用绝对价差判断时，几乎所有品种都会被划为 contango 或 backwardation。另外 `basis=0.0` 会因为 `or` 被跳过，改用 basis_rate。
  5. **市场环境取自区间末日**：context 按 `period.end` 拉取一次，区间内每一笔交易都用这个末日状态（技术指标、单日涨跌）评定顺逆势和执行质量。区间复盘时，早期交易是按事后的市场状态来评判的（后见之明）。日度复盘中盘中交易用当日收盘的数据评判，也属于同一问题。
  6. **全胜时评分反而下降**：`_compute_summary` 遇到 PF 为无穷大时输出 None，`_compute_score` 再把 None 当作 1.0，PF 项 `tanh(0)=0`。全胜账户的 PF 分项因此与盈亏平衡账户相同。没有平仓的情况下 PF 也记 1.0。
  7. **未知期货品种静默使用乘数 1**：`FUTURE_SPECS` 中没有的期货品种（例如 SA、FG、SR、AP、LC、SI 等常见品种）会被归为 `future_cn`，乘数为 1。注释说"由上游 warning"，但上游只对 `asset_type=="unknown"` 报警，所以这些品种的浮盈亏和敞口被低估 5 到 20 倍，没有任何提示。已列入字典的 27 个乘数逐一核对，与交易所规格一致。
  8. **策略意图层已整体失效**：`strategy_review_out` 始终为 None，合并代码被 `if False:` 包住；而且只有在 `is_empty()` 为真时才进入这段分支，条件本身也写反了。`.py` 策略文件会被 `exec_module` **直接执行**（加载即运行任意代码）；即使策略层失效，`load_strategy` 在传入 strategy_path 时仍会被调用。
  9. RSI 和 ATR 用简单移动平均，不是 Wilder 平滑，数值与通用软件不同；ATR 计算了两次。
  10. 测试：15 个用例都是脚本式断言，用 `__main__` 驱动，不是 pytest 收集。`test_preflight_accepts_config_credentials` 传入的是空白凭据，能通过只是因为设置了 `disable_context_fetch`，与"接受 config 凭据"这个名字不符。
- **结论更新**：数值与叙述分离、证据键可定位这两条可借鉴的做法不变。规则层中的 regime 单位错误、期货用股票趋势判断、基差单位混用和区间末日后见之明，使"顺逆势和执行质量"这类标签**不可信**。标记价必须来自同一合约，未知乘数必须阻断，这两点可直接作为 V1.2 RiskExecution 对账的反例用例。

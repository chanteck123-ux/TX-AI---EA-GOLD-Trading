# A130 skill-llm-alpha-generator（LLM 公式化因子挖掘）— 文本审核

## P0134 部分（FILE 1368 portable-loader、1369 README.en、1370 README、1371 references/data_guide 全文）

要点：
- 流程：LLM 生成候选公式 → 白名单、量纲与前视检查 → GP warm-start 精修 → AlphaEval 五维评分（预测、稳健、可解释、多样、简洁）→ LLM 经济解释 → HTML 报告。
- 所有 LLM 阶段都是强制的：任何一步失败即终止，不发布报告，不用 0.5 中性分或模板解释顶替。
- 外部 LLM 配置的唯一入口是 config.llm（四个字段必须齐全）；否则使用宿主模型。

初步发现：
1. **标签与执行时点**：`future_return = close.shift(-h)/close - 1`，默认 h=1。因子在 t 收盘计算，又以 t 收盘为起点计收益，等于假设能按信号当根收盘价成交（与套件其他资产反复出现的同类问题相同）。另外文档只做 IC 评估，没有说明标签需要错开一根。
2. **NaN/Inf 用前值或 0 兜底**：0 对于比率/收益类特征是有意义的数值，会把缺失伪装成"无变化"；前值填充在停牌期会造成平台段。这些都会影响 IC。
3. **口径矛盾**：README 说因子结果包含"样本内外指标"，data_guide 却说"只做样本内评估、不做回测"。样本外如何切分、是否预留，文档没有交代，待后续 references 核对。
4. 量纲投票中 LLM 权重 1.2，高于统计 1.0 和命名 0.6；confidence < 0.5 时记为 unknown。LLM 的判断可以压过统计画像，可复现性取决于模型版本，而 meta 虽记录 request_id 与 payload_hash，**没有记录温度和种子**（待后续核对 llm_policy）。
5. amount 缺失时用 volume·close 兜底：期货缺少合约乘数，成交额量纲会错。
6. 数据层失败时"返回空 DataFrame + warning、不抛异常"，与 LLM 层"失败即致命"的策略不同；不过 run() 无数据即终止，最终不会发布。
7. 传入列表 universe 时只取第一个标的，**静默截断**。
8. 合成数据"带已知动量信号"，只能证明管线跑得通，不证明方法有效；文档也已声明合成数据不得作为结论。

待续：P0135 读取 fitness_guide、llm_policy、method_guide、operator_spec、output_contract、review_checklist、requirements、SKILL.md。

## P0135 补读（FILE 1372–1379 全文：fitness_guide、llm_policy、method_guide、operator_spec、output_contract、review_checklist、requirements、SKILL.md）

要点：
- GP 适应度：`|rankIC|×(1−0.15·turnover) − 0.2·max|corr(精英)| − min(0.005·(节点−30), 0.1)`；有效样本少于 30 时记为 0。
- AlphaEval：`0.40·pps + 0.20·pfs + 0.20·rre + 0.15·logic + 0.05·diversity`。
- 算子白名单 22 个；三层校验：白名单 → 量纲 → 前视。前视层只检查"窗口 n ≥ 0"。

发现（续）：
9. **`rank(x)` 是校验器拦不住的前视**（operator_spec）：
   - 单标的时序中，`rank` 退化为"整段 pct rank"，用到了全样本（包括未来）的分布；
   - 前视层只拦负窗口，因此任何含 `rank()` 的公式都会带全样本信息；
   - IC 偏乐观，而且不能实盘复现。
   - 这是本资产最严重的问题（静态推导，scripts/operators.py 未读，未运行验证）。
10. **LLM 政策自相矛盾**：
    - "Mandatory Runtime Contract"、README、SKILL.md 的 LLM Rules、review_checklist 都写"禁止 enabled/provider、禁止纯 GP、禁止 logic=0.5 中性分"；
    - 但同一份 llm_policy 的示例用了 `enabled:True, provider:"agent"`，第 6 条硬约束写"纯 GP 可跑……logic 中性 0.5"，还给出"降级占位"；
    - fitness_guide 写"无 LLM→0.5、绝不抛异常"；
    - output_contract 的验收写"LLM 关闭时 factors 仍产出（纯 GP），interpretability=0.5"；
    - SKILL.md 的 Run 示例本身就是"纯 GP（不启用 LLM）"，Purpose 第 7 步写"LLM 经济解释（可选）"。
    - 新旧两层政策没有合并，实际行为只能看代码，**文档不可作为依据**。另外"LLM 参与的三处"的表格列了四处。
11. **rre 门槛的理由错误**：文档称 base_ic < 0.02 "明显高于大样本随机信号的 IC 噪声地板 ~1/√n"。两年日频约 480 个样本时 1/√480 ≈ 0.046，**0.02 远低于噪声地板**，因此门槛无法区分噪声与信号。
12. **用 |rankIC| 选择且没有样本外**：
    - 适应度取绝对值，符号由事后决定；
    - GP 在同一段样本内反复演化，并按 IC 选出 top_k，没有多重检验校正（文档承认，交给"回测 skill"）；
    - method_guide 说"只用 training slice 做 GP warm-start"，但其他文件都没有定义训练/验证切分，README 却称输出"样本内外指标"。
    - 口径前后三处不一致。
13. 算子的语义问题：
    - `protected_div` 在分母接近 0 时返回 1.0（而不是 NaN），引入假值；
    - `log(|x|+eps)` 丢掉了符号；
    - `if_then_else` 的 cond 不受量纲约束；
    - `mul`/`div` 的结果一律记为 ratio，使量纲校验大幅放宽。
14. requirements 没有钉版本，同时依赖 gplearn 与 deap；`anthropic` 列为强制依赖，与"未配置外部模型时用宿主模型"不一致。
15. 宿主模型的 agent_payload 由 agent 自己填写公式与解释，`"model": "current-agent"` 无法核实是哪个模型；README 所说的 request_id、payload_hash 对宿主模式能否记录，**未说明**。

**A130 结论**：文本全部覆盖（共 12 份全文）。管线的组织方式（白名单、量纲、拒绝原因分层）值得参考，但存在 `rank()` 全样本前视、单标签当根收盘执行、只做样本内且用绝对 IC 选择、LLM 政策文档互相矛盾等问题，**结果不能作为因子有效性证据**。与 EA 的关系：可借鉴"拒绝分层记录"（rejected.layer）用于候选登记；LLM 不进入 MQL5 执行端，**未实现**。

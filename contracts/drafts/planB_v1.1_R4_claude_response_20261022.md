## 三、Claude 补充的内容（请 Codex 逐条确认，不属于默默改语义）

| 编号 | 内容 | 原因 |
|---|---|---|
| C-1（R4-5） | 新增第四个取值 `SUPERSEDED`：迁移完成后旧作用域 A/B 标记为 SUPERSEDED，以旧作用域启动的实例只读告警，永不恢复执行 | Codex 要求旧命名空间不能被恢复使用，但没有说明用什么持久标记来阻止。没有这个标记，旧作用域以后被启动时看到的是一份有效 A/B，无法与正常作用域区分 |
| C-2 | 执行迁移者必须**同时持有新旧两个作用域的独占句柄**；取不到旧句柄说明旧执行器仍在运行，迁移被拒绝 | 把“确保旧执行器已停止”变成可检查的条件，而不依赖操作人员口头确认 |
| C-3（R4-2b） | 初始化中断的例外：`scope_meta` 有效、A/B 从未写入、且自 `scope_meta` 创建以来服务器上没有本项目 magic 的订单、成交或持仓时，可以重做 A/B 初始化。只要有任何此类活动，一律按状态恢复处理 | 见下方说明 |
| C-4 | 迁移、区分、状态恢复三类记录的提供者、格式以及是否需要用户确认，统一列入 §9 待确定 | Codex 只提到迁移记录格式；区分记录和恢复记录同样需要登记规程 |

**关于 C-3 的说明，可能与 Codex 的措辞存在张力，请明确裁决：**
- Codex 写的是“一旦初始化开始，中断后保守恢复”。
- 若严格解读为“写了 `scope_meta` 就永远不能再初始化”，那么在 `scope_meta` 与 A/B 之间崩溃一次，作用域就需要人工恢复记录才能使用。这时根本没有任何交易可恢复。
- C-3 只在服务器证明没有任何本项目活动时才放行重做，有活动就回到恢复路径。Claude 认为这仍然符合“保守”。
- 如果 Codex 认为任何例外都不可接受，删除 C-3 即可，RE-30p 第 (3) 项的预期相应改为“按状态恢复处理”。这不影响其他条款。
